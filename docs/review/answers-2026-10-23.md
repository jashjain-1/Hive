## Section 1 — Transport and client reach

**A1.** Today Hivemind exposes a legacy SSE endpoint at `/sse`. The interfaces that should be able to
use that URL today **without installing a local binary** are the ones that accept a remote SSE/HTTP MCP
endpoint:
- **Claude Desktop** — works via its MCP configuration pointing at the remote SSE URL.
- **Cursor** — works when configured with a remote MCP endpoint over SSE/HTTP.
- **Windsurf** — same pattern as above, remote endpoint configured in the client.
- **Antigravity** — same pattern, remote endpoint configured in the client.

These do **not** need a local binary; they need the hosted endpoint URL and a client config step.

Interfaces that should **not** be counted as "no-download" from a single hosted URL today:
- Any client that only supports **stdio** MCP with no usable remote MCP path.
- Clients that require a local MCP process launched from a local build artifact.

Concretely: SSE reaches the four named AI coding clients above; a client that only works over stdio is out
of scope for the "paste a URL and go" claim.

**A2.** If I wanted a single hosted URL to work in the broadest set of modern clients, I would **add
Streamable HTTP alongside SSE, and keep both** for now. I would **not** replace SSE yet.

Why keeping both matters:
- SSE is the current legacy transport and is already wired.
- Streamable HTTP is the newer direction many clients are moving toward.
- Ripping SSE out too aggressively would shrink reach before we know which clients have migrated.

What breaks if we switch too aggressively:
- Clients still on SSE lose connectivity.
- We would be optimizing for a client population we have not verified.
- The safer move is dual-transport now, SSE-first compatibility, and Streamable HTTP as the broadening path.

**A3.** For the intended deployment:
- The **hosted endpoint should eventually be HTTPS-only**.
- **TLS is terminated by the platform (Render)** for the hosted path; the server itself can run over plain HTTP
  behind that proxy.
- For **local testing**, plain HTTP on localhost is acceptable.

So: platform TLS termination for hosted; localhost HTTP OK for dev.

## Section 2 — No-download / plug-and-play use

**A4.** The primary persona for "plug and play, no download" is:

**A developer already in an AI coding client** (Claude Desktop, Cursor, Windsurf, Antigravity, etc.).

Secondary persona:
- A non-technical user who can open a hosted URL in a browser for status/preview/approval, but that is the
  secondary visibility surface, not the primary day-to-day story.

I am explicitly **not** making the completely non-technical user with zero client access the primary persona.

**A5.** Smallest possible first-run flow for the primary persona, 3 steps or fewer:

1. **Open the hosted dashboard or the endpoint URL** and confirm the server is live (health + status).
2. **Point the existing AI coding client at the hosted endpoint**, or enable the Hivemind skill where supported.
3. **Ask Hivemind something** through the client — for example `pack "fix the auth bug"` or `find "JWT"` —
   and see a result with NEXT_HOPS.

So: see it's alive → connect the existing client → use it. That is the 3-step target.

**A6.** The biggest friction point today is:

**Knowing whether it connected, and knowing what to ask it next.**

Finding the URL and configuring the client are real but secondary. The more important UX problems are:
- No clear connection/health signal the user can trust.
- No visible indexing/job state.
- No obvious next action when the user first lands on the endpoint.

That is why visibility/observability endpoints and the hosted dashboard are in scope before richer interactive
UI hooks.

## Section 3 — UI and interaction

**A7.** I want user interaction to live in **both** surfaces, with a clear split:

- **(a) Inside the AI chat client** — day-to-day tool use: `peek`, `expand`, `find`, `pack`, `explain`,
  `impact`, `next`, plus the governance path for risky actions when the client supports approval flows.
- **(b) A separate hosted web dashboard** — status and governance first: connection/health, indexing status,
  search/preview, context-pack review, blast radius, and approval recording.

The split:
- Tool use and normal context retrieval live in the client.
- Status, visibility, preview, and approval recording live in the hosted dashboard.

I do **not** want the dashboard to become a full second app; it is the browser-only persona surface.

**A8.** The Hivemind actions a non-technical user should be able to trigger directly through a UI, without an
agent intermediary:

- **View connection/health state.**
- **View indexing status and job progress.**
- **Search a repo and preview results.**
- **Preview / review a context pack.**
- **View blast radius / impact for a change.**
- **Start an indexing job** (where appropriate).

These are the read-oriented and status-oriented actions. Riskier mutations are handled separately.

**A9.** For risky tool calls (`write`, `branch`, `pin`):

**The UI should let the user see and approve risky tool calls before they happen**, at least by default.

So: visibility + approval by default for risky mutations. Agent autonomy for those is acceptable only after the
user has explicitly trusted the system, and even then there should be a record of what was approved.

This is why `/rbac/v1/propose`, `/rbac/v1/approve`, `/rbac/v1/pending`, and `/rbac/v1/records` exist: they
give the dashboard a visible approval surface rather than an invisible agent-only path.

## Section 4 — Skills and portability

**A10.** I want Hivemind to be consumed as **both**:

1. **An MCP server** — the current implementation, reached via SSE or Streamable HTTP.
2. **A portable agent skill package** — a `SKILL.md`-style artifact that travels to the client.

What the skill package should do that the MCP server alone does not:
- Describe **what Hivemind is** and **when to use it**.
- Describe **how to call the remote Hivemind endpoint** (transport + endpoint + basic enable steps).
- Include a **short fallback note** for when no remote server is available.

The skill should **not** imply a full local MCP experience exists when it does not.

So: MCP server is the runtime; the skill is the portable description + enable guidance.

**A11.** If I published a portable skill for Hivemind, today the realistic discovery/enable path is:

- **A repo-based portable skill**, plus clear enable instructions.

Today I am **not** assuming a skills registry or client marketplace exists for every target client. Those are the
nicer future path, but the current pragmatic path is repo-based + enable instructions.

So: repo-based skill + enable instructions now; registry/marketplace later if/when the target clients support it.

**A12.** The skill should **describe how to call the remote Hivemind endpoint**, and **also include a short
fallback note** when no remote server is available.

It should **not** pretend there is a complete local MCP fallback when there isn't one.

So: remote-first description, with an honest fallback note.

## Section 5 — Scope and priorities

**A13.** If I could only complete three of these gaps —
Streamable HTTP, interactive UI hooks, hosted dashboard skeleton, portable skill asset, visibility/approval
endpoints — I would pick, in this order:

1. **Streamable HTTP** — broadest client reach for the hosted URL.
2. **Visibility/approval endpoints** — solves the "did it connect / what is happening / can I approve risky
   actions" problem for the browser-only persona.
3. **Hosted dashboard skeleton** — gives the browser-only persona a usable surface for the above.

Then, after those three:
- Portable skill asset.
- Interactive UI hooks on the highest-value tools.

So the current order is: Streamable HTTP → visibility/approval → hosted dashboard → portable skill → interactive
hooks.

**A14.** For the hosted free tier, I am **comfortable with ephemeral tenant storage and an on-demand model
warm-up**, as long as:
- It is **documented explicitly**, and
- The **upgrade path to persistent storage is clear**.

So: ephemeral is acceptable for alpha/demo, not as a hidden behavior.

**A15.** Clients/platforms/personas I absolutely do **not** want Hivemind to target right now:

- **No promise of universal client support.** If a client only works via stdio or has no usable remote-MCP path,
  it is out of scope for the "no-download" claim.
- **No managed brokered connector / marketplace today.** That is a future product/infra step.
- **Not targeting a completely non-technical user with zero client access as the primary story.**

These are explicit exclusions so the scope stays honest.
